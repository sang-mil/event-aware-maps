# 협업 규칙과 정책 가이드

대상: 백엔드 담당(코드 이해 가능), 프론트 담당(코드 비이해), 구현 도구 Claude Code. 이 문서가 저장소의 단일 기준이며, 바꿀 때도 PR로만 바꿉니다.

## 0. 핵심 원칙

1. **main은 항상 동작하는 상태**로 유지하고 직접 푸시하지 않습니다.
2. 모든 변경은 **이슈 → 브랜치 → PR → 리뷰 → 머지** 순서로만 들어갑니다.
3. **JSON 스키마(데이터 계약)가 먼저**입니다. 바꾸려면 별도 절차를 거칩니다.
4. **한 PR은 한 목적**, 작게 만듭니다.
5. 코드를 몰라도 승인할 수 있어야 합니다. 그래서 모든 PR에는 "화면에서 확인하는 방법"이 들어갑니다.
6. Claude가 쓴 코드도 **사람의 책임**입니다. 사람이 PR 설명을 읽고 승인한 것만 머지합니다.
7. 막히면 숨기지 않고 이슈에 `status:blocked`로 표시합니다.

## 1. 역할과 권한

| 역할 | 하는 일 | 권한 |
|---|---|---|
| 백엔드 담당 | 데이터·모델·추천 로직, 스키마 승인, 코드 리뷰, **최종 머지** | 저장소 관리자 |
| 프론트 담당 | 화면 요구 작성, Claude로 프론트 작업, **화면 확인 리뷰** | 쓰기(브랜치·PR 생성) |
| Claude | 이슈를 읽고 구현, PR 설명 작성, CI 실패 수정 | 사람이 지시한 이슈 범위 안에서만 |

- 프론트 담당은 코드를 읽지 못해도 됩니다. 대신 **스크린샷과 로컬 실행 체크리스트**로 승인합니다.
- 백엔드 담당은 프론트 PR의 코드도 훑어보고 머지합니다(폴더 밖 수정, 이상한 의존성 추가 여부 확인).
- 서로의 PR을 **상대가 승인**해야 머지됩니다. 자기 PR을 자기가 승인하는 것은 금지입니다.

## 2. 저장소 구조 (모노레포)

```
/
├─ CLAUDE.md              Claude 공통 규칙
├─ README.md
├─ .claude/settings.json  Claude Code 권한 설정
├─ .github/
│   ├─ ISSUE_TEMPLATE/
│   ├─ pull_request_template.md
│   ├─ CODEOWNERS
│   └─ workflows/         CI, 배포, 데이터 갱신
├─ data-contract/         JSON 스키마 + 목업 JSON (BE·FE 약속)
├─ backend/               수집·정제·모델·추천 (CLAUDE.md 포함)
├─ frontend/              정적 웹 (CLAUDE.md 포함)
└─ docs/                  협업 규칙, 설계, decisions/
```

**폴더 소유 원칙**: `backend/`는 BE, `frontend/`는 FE만 수정합니다. `data-contract/`는 BE 승인이 있어야만 바뀝니다. 같은 파일을 둘이 건드리지 않게 하는 것이 충돌을 줄이는 가장 쉬운 방법입니다.

## 3. 브랜치 전략: 단순화한 GitHub Flow

`develop` 브랜치 없이 **main + 짧은 작업 브랜치**만 씁니다. 두 명이라 복잡한 전략은 비용만 큽니다.

### 3-1. 브랜치 이름

`타입/이슈번호-짧은설명` 형식입니다.

| 타입 | 용도 | 예시 |
|---|---|---|
| feat | 새 기능 | `feat/12-recommend-card` |
| fix | 버그 수정 | `fix/27-time-format` |
| data | 데이터·모델 변경 | `data/31-overlap-detector` |
| contract | 스키마 변경 | `contract/8-add-confidence` |
| docs | 문서 | `docs/40-readme` |
| chore | 설정·도구 | `chore/5-ci-setup` |

- 브랜치 수명은 **3일 이내**. 길어지면 이슈를 쪼갭니다.
- 이슈 하나당 브랜치 하나, 브랜치 하나당 PR 하나입니다.

### 3-2. main 보호 규칙 (GitHub 설정)

- PR 없이 푸시 금지, force push 금지, 브랜치 삭제 금지
- 승인 1명 이상(작성자 본인 제외)
- CI 전부 통과해야 머지 가능
- 리뷰 코멘트가 모두 해결되어야 머지 가능
- 머지 방식은 **Squash merge**만 허용, 머지 후 브랜치 자동 삭제

### 3-3. 자동 생성 데이터는 분리

배치가 5~10분마다 JSON을 갱신하면 main 히스토리가 지저분해집니다. **예보 JSON은 별도 `gh-pages`(산출물 전용) 브랜치에만 기록**하고, main에는 코드와 목업만 둡니다. 프론트는 이 브랜치의 JSON을 읽습니다.

## 4. 이슈 정책

**이슈는 Claude에게 그대로 넘길 수 있는 작업 지시서**입니다. 모호한 이슈는 모호한 코드를 만듭니다.

### 4-1. 이슈 종류

| 종류 | 언제 | 템플릿 |
|---|---|---|
| 기능 | 새 화면·로직 | 목표, 완료 조건, 하지 말 것 |
| 버그 | 의도와 다르게 동작 | 재현 방법, 기대 결과, 실제 결과, 스크린샷 |
| 스키마 변경 | 데이터 계약 수정 | 변경 이유, 전후 비교, 영향 범위 |
| 작업 | 설정·문서·정리 | 할 일, 완료 조건 |

### 4-2. 라벨

- 영역: `area:be`, `area:fe`, `area:contract`, `area:ops`
- 타입: `type:feature`, `type:bug`, `type:chore`, `type:docs`
- 우선순위: `P0`(지금 막힘), `P1`(이번 주), `P2`(여유 있을 때)
- 상태: `status:blocked`, `status:needs-info`, `status:ready`(Claude에게 넘겨도 됨)

### 4-3. 이슈 작성 규칙

- 제목은 결과로 씁니다: "추천 카드 화면 만들기" (O) / "카드 관련" (X)
- **완료 조건은 눈으로 확인 가능한 문장**으로 씁니다: "1순위 카드에 출발 시각과 노선이 표시된다"
- **하지 말 것**을 적습니다: "혼잡 수치를 화면에서 계산하지 않는다"
- `status:ready`가 붙은 이슈만 Claude에게 넘깁니다.
- 마일스톤은 `MVP-1`, `MVP-2`, `마감`으로 나눕니다.

## 5. 커밋 규칙

`타입: 한 줄 요약` 형식이고 한국어로 씁니다. Claude에게도 같은 규칙을 시킵니다.

```
feat: 추천 카드 1순위·대안 표시 (#12)
fix: 종료 시각 시간대 오류 수정 (#27)
data: 겹침일 판별 로직 추가 (#31)
```

- 커밋은 PR 안에서 squash 되므로 **PR 제목이 최종 기록**입니다. PR 제목은 위 형식을 지킵니다.
- 본문 마지막에 `Closes #이슈번호`를 넣어 이슈가 자동으로 닫히게 합니다.

## 6. PR 정책

### 6-1. 크기와 형식

- 변경 **300줄 이내, 파일 10개 이내**를 권장합니다. 넘으면 쪼갭니다.
- 작업 중에는 **Draft PR**로 올리고, 끝나면 Ready로 바꿉니다.
- PR 설명은 템플릿을 따르며, **비개발자가 읽고 이해할 수 있는 말**로 씁니다(Claude에게 그렇게 시킵니다).

### 6-2. 리뷰 방식

| 작성자 | 리뷰어가 보는 것 |
|---|---|
| 프론트(Claude 사용) | BE: 폴더 밖 수정 여부, 의존성 추가, 스키마 준수 / FE: PR 스크린샷과 로컬 실행으로 체크리스트 확인 |
| 백엔드 | FE는 코드를 보지 않아도 됩니다. 단, 화면에 영향이 있으면 스크린샷으로 확인 |

- 프론트 담당의 승인 기준은 단 하나입니다: **PR 설명의 "확인 방법"대로 했을 때 그대로 되는가**.
- 리뷰는 **24시간 안에** 첫 응답을 합니다. 어렵다면 "이틀 걸려요"라고 남깁니다.
- 코멘트가 이해되지 않으면 Claude에게 "이 코멘트가 무슨 뜻인지 쉽게 설명해줘"라고 물어도 됩니다.

### 6-3. 머지 조건 (모두 충족)

1. CI 전부 초록
2. 상대방 승인 1건
3. 스키마 변경이 있으면 BE 승인
4. 코멘트 전부 해결
5. 최신 main과 충돌 없음 (충돌은 BE가 Claude에게 해결을 시킵니다)

### 6-4. 미리보기 링크 없이 확인하는 방법

PR별 미리보기 링크는 만들지 않습니다. 대신 아래 순서로 확인합니다.

1. **스크린샷(필수)**: 화면이 바뀌는 PR은 Claude Code가 변경 전·후 스크린샷을 찍어 PR 설명에 첨부합니다. 리뷰어는 먼저 사진을 보고 이슈의 완료 조건과 비교합니다. 촬영은 Playwright 같은 브라우저 자동화 도구로 하고, 설치는 BE가 한 번만 세팅합니다.
2. **로컬 실행(필요할 때)**: 사진만으로 부족하면 프론트 담당이 자기 Claude Code에 "이 PR 브랜치를 받아서 실행하고, 확인 방법 1번부터 같이 해보자"라고 시킵니다. 이때 화면은 `data-contract/`의 목업 JSON으로 뜹니다.
3. 클릭·입력처럼 사진으로 알 수 없는 동작이 바뀌는 PR은 **단계별 스크린샷**을 남깁니다.
4. 실제 데이터로 보는 최종 확인은 **머지 후 main 배포본**에서 합니다. 문제가 있으면 `type:bug` 이슈를 올리고, 급하면 되돌리기(revert) PR을 만듭니다.

## 7. 스키마(데이터 계약) 변경 절차

`data-contract/`의 JSON Schema와 목업이 **BE와 FE의 유일한 약속**입니다.

1. `스키마 변경` 이슈를 만들고 이유와 전후 비교를 씁니다.
2. **BE만** 스키마 PR을 올리고 승인합니다. FE는 스키마를 수정하지 않습니다.
3. 필드 **추가**는 자유롭게, **삭제·이름 변경·의미 변경**은 버전을 올립니다(`v1` → `v2`).
4. 스키마 PR에는 **목업 JSON 갱신이 반드시 포함**됩니다. 목업이 스키마를 통과하지 못하면 CI가 실패합니다.
5. 머지되면 FE 이슈를 새로 만들어 반영합니다.

## 8. Claude 사용 규칙

### 8-1. 공통 원칙

- **세션 하나에 이슈 하나**만 처리합니다. 여러 이슈를 섞지 않습니다.
- 시작은 항상 **"계획 먼저"**입니다. 이슈를 읽게 한 뒤 계획을 받아 사람이 확인하고, 그다음에 구현합니다.
- 작업이 끝나면 **바뀐 파일 목록과 이유, 화면에서 확인하는 방법**을 보고하게 합니다.
- 저장소에 `CLAUDE.md`를 두어 매번 같은 규칙이 적용되게 합니다.

### 8-2. 금지 사항

- main 직접 푸시, force push, 다른 사람 브랜치 수정
- 이슈 범위를 벗어난 수정("겸사겸사 정리" 포함)
- 승인 없는 **의존성(라이브러리) 추가**
- API 키·토큰·비밀번호를 코드나 문서에 쓰기
- 테스트를 지우거나 무력화해서 CI를 통과시키기
- **수치·통계·데이터를 지어내기**: 모든 숫자는 출처(파일, API)가 있어야 하고, 모르면 "모른다"고 보고합니다.
- FE 작업 중 `backend/`, `data-contract/` 수정 (BE 작업 중 `frontend/` 수정도 동일)

### 8-3. 프론트 담당용 프롬프트 습관 (코드를 몰라도 되는 방법)

1. 이슈 번호를 알려줍니다: "이슈 #12를 읽고 작업 계획부터 쉬운 말로 설명해줘."
2. 계획이 이해되면: "좋아, 진행해. 끝나면 내가 화면에서 확인할 방법을 알려줘."
3. 막히면 에러를 **그대로 복사해서** 붙입니다: "이 오류가 뭔지 쉬운 말로 설명하고 고쳐줘."
4. 모르는 용어는 바로 묻습니다: "방금 말한 ○○가 뭐야?"
5. 마지막에는 항상: "PR 설명을 비개발자가 읽기 쉽게 써줘."

### 8-4. Claude Code 운영 규칙

- **저장소 루트에서 실행**해 `CLAUDE.md`가 항상 자동으로 읽히게 합니다. 두 사람 모두 저장소를 clone해서 씁니다.
- 이슈 작업은 **계획 모드(plan mode)에서 시작**합니다. 읽기만 하고 계획을 낸 뒤, 사람이 승인하면 실행으로 넘어갑니다.
- PR 생성과 CI 로그 확인은 `gh` CLI로 Claude Code가 합니다(최초 1회 `gh auth login`). **머지는 사람만** 합니다.
- 권한 설정은 저장소의 `.claude/settings.json`에 커밋해 두 사람이 같은 설정을 씁니다. `git push --force`, main 푸시, `rm -rf`, `.env` 읽기는 거부(deny) 목록에 넣습니다.
- **세션 하나에 이슈 하나**입니다. 이슈가 끝나면 새 세션을 시작해 앞 작업의 맥락이 섞이지 않게 합니다.
- 작업 전에 `git pull`로 최신 main을 받고, 브랜치는 Claude Code가 이슈 번호로 만들게 합니다.

## 9. CI(자동 검증)

PR을 올리면 자동으로 돌고, **하나라도 빨간불이면 머지할 수 없습니다.** 코드를 모르는 사람은 "초록이면 통과, 빨강이면 Claude에게 로그를 보여주고 고쳐달라고 하기"만 알면 됩니다.

- 문법·스타일 검사(lint)와 타입 검사
- 테스트(백엔드 로직, 프론트 주요 화면)
- **스키마 검증**: 모든 목업·산출 JSON이 스키마를 통과하는지
- 빌드 성공 여부
- 시크릿 유출 검사
- 프론트 PR은 Claude Code가 찍은 화면 스크린샷을 PR에 첨부합니다.

## 10. 보안·데이터 정책

- API 키는 **GitHub Secrets**에만 두고, `.env`는 `.gitignore`에 넣습니다. 한 번이라도 커밋되면 키를 즉시 폐기하고 재발급합니다.
- 공공데이터 **원본 대용량 파일은 커밋하지 않습니다.** 필요하면 수집 스크립트와 샘플 일부만 둡니다.
- 모든 데이터의 **출처와 이용 조건**을 `docs/data-sources.md`에 기록하고, 화면 하단에도 출처를 표기합니다.
- 사용자 위치·개인정보는 **서버로 보내지 않습니다.** 출발지는 프리셋 선택만 받고, 서버가 없는 구조를 지킵니다.

## 11. 소통과 의사결정

- 모든 논의는 **이슈·PR 코멘트에 남깁니다.** 메신저에서 정한 것은 한 줄로 요약해 이슈에 옮깁니다.
- **주 1~2회, 15분** 동기화: 지난 것, 이번 것, 막힌 것만 이야기합니다.
- 기술·방향 결정은 `docs/decisions/번호-제목.md`에 **5줄로** 남깁니다(상황, 선택지, 결정, 이유).
- 의견이 갈리면: 사용자(시민) 화면 관련은 FE 담당 의견을, 데이터·로직 관련은 BE 담당 의견을 우선합니다.

## 12. 저장소 초기 세팅 체크리스트

1. 저장소 생성, 두 명 초대, main 보호 규칙 설정
2. 폴더 구조와 `README.md`, `CLAUDE.md`(루트·backend·frontend) 작성
