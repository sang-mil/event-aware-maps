# 초기 설계서: 잠실·올림픽공원 귀가·이동 안내

첫 목표(MVP-1)는 **가짜 데이터로 끝까지 도는 뼈대**입니다. 계산은 BE, 표시는 FE, 둘의 약속은 `data-contract/`가 맡고, 협업 규칙 가이드(`docs/COLLABORATION.md`)의 정책이 구조에 그대로 반영됩니다.

## 1. 정책을 설계에 연결하기

| 협업 정책 | 설계에 반영된 방식 |
|---|---|
| 스키마가 먼저 | 이슈 #3에서 스키마 v1과 목업 JSON을 먼저 만들고, BE·FE가 그 위에서 병행 개발 |
| 계산은 BE, 표시는 FE | FE는 JSON만 읽고 순위·혼잡 수치를 계산하지 않음 (문구도 BE가 생성) |
| 폴더 소유 | `backend/` BE, `frontend/` FE, `data-contract/` BE 승인 |
| 이슈는 작게 | 첫 백로그를 이슈 11개로 쪼개고 의존 관계를 명시 (7절) |
| 운영비 0원, 서버 없음 | GitHub Actions 배치 + 정적 호스팅, 서버·DB 없음 |
| 마지막 정상값 유지 | 발행 직전 스키마 검증, 실패하면 기존 JSON을 덮어쓰지 않음 |
| 개인정보 서버 전송 금지 | 출발지는 프리셋 선택만 받고 GPS는 쓰지 않음 |
| 비개발자 리뷰 | FE 이슈마다 화면에서 확인할 완료 조건과 스크린샷 첨부 |

## 2. 전체 구조

```
[공공데이터·API]
      │  (GitHub Actions: 평시 매일, 행사일 5~10분 주기 요청)
      ▼
backend  수집 → 정제 → 이벤트 엔진 → 혼잡 모델 → 추천 엔진
      │
      ▼  스키마 검증 통과한 것만 발행
gh-pages 브랜치 /data/*.json   ◀── 사람이 직접 수정하지 않는 산출물 브랜치
      ▲
      │  fetch (같은 도메인, 서버 없음)
frontend  정적 웹(/)  ── 같은 gh-pages 브랜치에 배포
```

- **배포 단위는 둘**입니다. FE는 main 머지 때, 데이터는 배치 때 각각 `gh-pages`에 쓰며 서로의 파일을 지우지 않습니다.
- `gh-pages`는 산출물 전용이라 main 히스토리가 지저분해지지 않습니다(정책 3-3절).
- **리플레이 모드는 같은 코드로 나옵니다.** BE의 모든 계산 함수가 `as_of`(기준 시각)를 인자로 받게 설계하면, 과거 날짜를 넣는 것만으로 2025-05-17 같은 날의 예보가 만들어집니다.

## 3. 데이터 계약 v1 (`data-contract/`)

### 3-1. 파일 구성

| 파일 | 내용 | 갱신 |
|---|---|---|
| `meta.json` | 스키마 버전, 최종 갱신 시각, 데이터 출처 목록 | 배치마다 |
| `presets.json` | 출발지·방향 프리셋(id와 한국어·영어 이름) | 수동(BE) |
| `calendar.json` | 날짜별 행사 목록과 겹침 여부(D-7 알림 근거) | 하루 1회 |
| `forecast/YYYY-MM-DD.json` | 그날의 행사, 시간대별 혼잡, 프리셋별 추천 | 행사일 5~10분 |
| `notice/YYYY-MM-DD.json` | 국·영문 퇴장 분산 안내 문구 | 하루 1회 |
| `backtest.json` | 추정 정확도, 수용률별 시뮬레이션 | 수동·주 1회 |

스키마는 `schema/*.schema.json`, 목업은 `mock/*.json`에 둡니다. **목업이 스키마를 통과하지 못하면 CI가 실패**합니다.

### 3-2. 공통 규칙

- 모든 시각은 **오프셋이 붙은 ISO 형식**(`2025-05-17T21:10+09:00`)입니다. 자정을 넘기는 귀가 시간 때문에 `HH:MM`은 쓰지 않습니다.
- 장소·역·노선은 한글 이름이 아니라 **id**로 참조하고, 표시용 이름은 `presets.json`에서 찾습니다.
- `level`은 1~5 정수입니다(1 여유, 5 매우 혼잡). 색과 숫자의 병기는 FE가 합니다.
- 모르는 값은 **키를 지우지 않고 `null`** 로 두고, `confidence`(`scheduled` / `estimated` / `corrected`)로 신뢰도를 표시합니다.
- 사용자에게 보이는 문장은 `message_ko`, `message_en`으로 BE가 만들어 줍니다.
- 필드 **추가는 자유, 삭제·이름 변경·의미 변경은 v2**입니다(정책 7절).

### 3-3. `forecast` 예시

```json
{
  "schema_version": "1.0",
  "date": "2025-05-17",
  "updated_at": "2025-05-17T21:05:00+09:00",
  "events": [
    {"venue_id": "kspo_dome", "end_at": "2025-05-17T21:10:00+09:00", "confidence": "estimated"}
  ],
  "congestion": [
    {"time": "2025-05-17T21:30:00+09:00", "line_id": "line9", "station_id": "sports_complex",
     "direction_id": "gangnam", "level": 4}
  ],
  "recommend": [
    {"from_id": "jamsil_baseball", "to_id": "gangnam_samsung",
     "options": [
       {"rank": 1, "depart_from": "2025-05-17T21:35:00+09:00", "depart_to": "2025-05-17T21:50:00+09:00",
        "route_id": "line2_sports_complex", "est_min": 28, "level": 2,
        "confidence": "estimated", "message_ko": "21:35~21:50 사이 2호선으로 가세요",
        "message_en": "Take Line 2 between 21:35 and 21:50"}
     ]}
  ]
}
```

출발 시각을 한 점이 아닌 **시간 창**(`depart_from`~`depart_to`)으로 둔 것은 추천이 한 시각에 쏠리는 문제를 줄이기 위해서입니다.

## 4. 백엔드 설계 (`backend/`)

```
backend/
├─ CLAUDE.md
├─ collectors/    소스별 파일 하나 (체육산업개발, 서울교통공사, 기상청, KBO, 서울시 실시간)
├─ normalize/     역·노선·시설 id 매핑, 시간대 표준화
├─ events/        겹침일 판별, 종료 시각 추정
├─ congestion/    혼잡 점수 (v0 규칙 → v1 통계 → v2 열차 단위)
├─ recommend/     비용 함수, 시간 창, 분산 로직
├─ nowcast/       당일 보정
├─ backtest/      정확도, 수용률 시뮬레이션
├─ publish/       스키마 검증 후 JSON 기록, 실패 시 기존 파일 유지
├─ cli.py         collect / build / publish 명령
└─ tests/ (fixtures/ 포함)
```

| 모듈 | 입력 | 출력 | 단계 |
|---|---|---|---|
| collectors | 외부 API·파일 | 원본 스냅샷 | MVP-1 |
| normalize | 원본 스냅샷 | 표준 테이블 | MVP-1 |
| events | 표준 테이블 | `calendar.json`, 종료 시각 | MVP-1 |
| congestion | 행사·승하차 통계 | 시간대×역×방향 점수 | v0는 MVP-1, v2는 MVP-2 |
| recommend | 혼잡 점수, 프리셋 | `forecast`의 `recommend` | MVP-1(단순), MVP-2(분산) |
| publish | 위 산출물 | 검증된 JSON | MVP-1 |
| nowcast, backtest | 당일 데이터, 2025 겹침일 | 보정값, `backtest.json` | MVP-2 |

**설계 원칙 세 가지**

1. 모든 계산 함수는 `as_of`를 받는 **순수 함수**로 만들어 리플레이와 백테스트를 같은 코드로 돌립니다.
2. 외부 호출은 `collectors/`에만 두고 나머지는 fixtures로 테스트합니다. API 키 없이 CI가 돕니다.
3. 혼잡 모델은 **v0 규칙 기반**(행사 종료 시각 + 고정 프로파일)부터 시작해 한 단계씩 정교하게 만듭니다. v0만으로도 화면과 스키마는 끝까지 돌아가야 합니다.

## 5. 프론트엔드 설계 (`frontend/`)

**제안 스택**: Vite + React + TypeScript, 순수 CSS, 상태 라이브러리 없음. Claude Code가 가장 안정적으로 다루는 표준 조합이고, 코드를 못 읽는 사람이 관리하기에 의존성이 적은 쪽을 골랐습니다.

- 라우팅은 GitHub Pages에 맞춰 **해시 방식**(`#/`, `#/today`, `#/replay`, `#/ops`)입니다.
- 데이터 타입은 **JSON 스키마에서 자동 생성**합니다. 스키마가 바뀌면 FE 빌드가 먼저 깨져서 어긋남을 바로 알 수 있습니다.
- 데이터 접근은 `src/api/` 한 곳에서만 하고, 로드 실패 시 마지막 캐시와 "n분 전 데이터"를 보여줍니다(빈 화면 금지).

| 화면 | 읽는 파일 | 단계 |
|---|---|---|
| 귀가 추천 (프리셋 선택 → 1순위 + 대안 2) | `presets`, `forecast` | MVP-1 |
| 오늘 이동 예보 (한 장 히트맵) | `forecast` | MVP-1 |
| 리플레이 (날짜 선택 + 시간 슬라이더) | `forecast` (과거 날짜) | MVP-2 |
| 운영자 (겹침 캘린더, 안내문 복사) | `calendar`, `notice` | MVP-2 |
| 공통: 갱신 시각, 신뢰도 배지, 한·영 전환, 색+숫자 병기 | `meta` | MVP-1 |

## 6. 브랜치·CI 연계

| 워크플로 | 실행 시점 | 하는 일 |
|---|---|---|
| `ci-contract` | `data-contract/` 변경 PR | 스키마 문법 검사, 목업 전부 검증 |
| `ci-backend` | `backend/` 변경 PR | lint, 테스트, 산출 JSON 스키마 검증 |
| `ci-frontend` | `frontend/` 변경 PR | lint, 타입 검사, 빌드, 목업 기반 화면 테스트 |
| `secret-scan` | 모든 PR | 키 유출 검사 |
| `deploy-frontend` | main 머지 | 빌드해서 `gh-pages` 루트에 배포 |
| `data-refresh` | 스케줄 + 수동 실행 | collect → build → publish, `gh-pages/data`에 기록 |

변경된 폴더에 해당하는 워크플로만 돌게(paths 필터) 하면 FE만 건드린 PR이 BE 테스트에 막히지 않습니다. API 키는 GitHub Secrets에만 둡니다.

## 7. 첫 이슈 백로그

라벨과 마일스톤은 정책 4절을 따릅니다. 1~4번이 끝나면 **FE(5·6·11)와 BE(7·8·9)가 병행**됩니다.

| # | 제목 | 영역 | 선행 | 완료 조건 (한 줄) |
|---|---|---|---|---|
| 1 | 저장소 초기 세팅 | ops | 없음 | 템플릿·CLAUDE.md·CODEOWNERS·문서가 main에 있다 (보호 규칙 켜기 전 직접 커밋) |
| 2 | 데이터 가용성 조사 | be | 없음 | 서울교통공사 통계의 시간 해상도, 열차 단위 여부, API 키 발급 여부를 결정 기록으로 남긴다 |
| 3 | 스키마 v1 + 목업 | contract | 1 | 3절 파일 전부의 스키마와 목업이 있고 서로 검증된다 |
| 4 | CI 뼈대 | ops | 1, 3 | 6절의 PR용 워크플로가 초록으로 돈다 |
| 5 | FE 앱 뼈대 | fe | 3, 4 | 목업 JSON을 읽어 갱신 시각과 오류·지연 상태가 화면에 나온다 |
| 6 | 귀가 추천 화면 | fe | 5 | 프리셋 선택 시 1순위와 대안 2개가 카드로 나온다 (스크린샷 첨부) |
| 7 | 수집기: 체육산업개발 공연·대관 | be | 2, 3 | fixtures로 파싱 테스트가 통과한다 |
| 8 | 이벤트 엔진: 겹침일 판별 | be | 7 | `calendar.json`이 스키마를 통과하고 2025년 겹침일이 확인된다 |
| 9 | 혼잡 v0 + forecast 발행 | be | 8 | `forecast`가 스키마를 통과하고 발행 단계에서 검증 실패 시 기존 파일이 유지된다 |
| 10 | 배포와 데이터 갱신 | ops | 6, 9 | `gh-pages`에서 화면이 실제 JSON으로 뜬다 |
| 11 | 오늘 이동 예보 한 장 뷰 | fe | 5 | 시간대별 혼잡이 색+숫자로 한 화면에 나온다 |

MVP-2는 열차 단위 모델, 분산 로직, 당일 보정, 백테스트, 리플레이, 운영자 화면, PWA 순서로 이슈를 만듭니다.

## 8. 위험과 미결정 사항

| 항목 | 내용 | 대응 |
|---|---|---|
| 데이터 해상도 | 열차 단위 추정이 불가능하면 모델 범위가 좁아짐 | 이슈 #2를 가장 먼저 하고 결과를 `docs/decisions/`에 기록 |
| Actions 스케줄 지연 | GitHub의 스케줄 실행은 정시를 보장하지 않고 몇 분 밀릴 수 있음. 공개 저장소는 60일간 활동이 없으면 스케줄이 멈출 수 있음 | 행사일에는 수동 실행을 병행하고, 시연 전에 최근 실행 여부를 확인 |
| 개발 스택 | Python(BE)과 Vite+React+TS(FE)는 제안일 뿐 | 이슈 #1에서 BE 승인 후 확정 |
| 프리셋 범위 | 출발지·방향 목록이 아직 없음 | BE가 1차안(출발지 3곳 × 방향 3개)을 만들고 이슈 #3에서 확정 |
| 대회 요건 | 제출 형식과 데이터 활용 규정은 이 문서에 반영되지 않음 | 공모 요강을 확인해 필요한 조항을 `docs/`에 정리 |
| 저장소 설정 | 비공개 저장소는 무료 플랜에서 보호 규칙 제한 가능 | 공개 여부를 확정한 뒤 보호 규칙 적용 |
